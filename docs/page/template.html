Token-Lean Code Layer

An MCP server and CLI that let an AI model read a codebase through a compact map, read only the code a task needs, and change it with small edit operations that the server applies, formats and type-checks.

Working name. Plan written 6 November 2026, with token counts measured the same day on a sample corpus (method and limits in Measured results).

Verdict

Build it, but not as a new language. The measurements on this page point to three conclusions:

  1. Most of the saving comes from choosing what to send and from the edit format, not from the syntax. The map of a file is 69-97% smaller than the file. An edit operation is 53-75% smaller than SEARCH/REPLACE blocks and 92-99% smaller than rewriting the file.
  2. For TypeScript and CSS, real code beats a custom syntax. Valid code without comments and indentation saves 24%. The custom compact syntax saves 21% (TypeScript) and 24% (CSS), and the model would have to learn it. Ship real code.
  3. For HTML and JSX, a compact view pays. Pug-style markup saves 19-20% against 7-14% for plain markup. Eliding inline SVG takes HTML to 53%.

The open question is accuracy. Token counts are measured; whether a model does the task as well with these views is not. Phase 5 of the roadmap answers it, and it is a go or no-go gate.

The idea

A model working on code spends tokens in two places. It reads files to find and understand the code, and it writes changes, often by repeating code it is not changing. Prompt caching makes repeated input cheap (a cached read costs about 10% of the normal input price on Anthropic's API), but it does not make it small. Every token still fills the context window and adds time. Output tokens cost about 5 times as much as input tokens and are never cached.

The layer sits between the model and the files. It gives the model three things:

  • A map (L0): one line per declaration, landmark or group of rules, with signatures and line ranges. The model reads it first to find what matters.
  • Views on request (L1): only the symbol, section or rules the task needs, in the cheapest form the model reads well.
  • Edit operations: small commands addressed by name. The server applies them to the original text, formats only what changed, type-checks, and rolls back on failure.

The model never converts code back to TypeScript, HTML or CSS. The server does. Code that the model did not edit stays byte for byte as it was.

Why syntax saves so little: what the tokenizer sees

Each chip is one token in o200k_base. Keywords, runs of spaces and common punctuation are already single tokens, so removing them saves only a few. Names, strings and class names make up most of the code, and no view can remove them.

Edits and addresses

The model edits by naming what it changes. The measurement showed that numeric IDs written into every line of a view cost 1-9 points of saving (9 for CSS, where every rule carried one). So IDs live only in the map, and code is addressed by name:

LanguageAddressExample operation
TypeScriptfile:Symbol.memberusers.ts:createUser insert-after stmt[1]: const email = parsed.data.email.toLowerCase()
JSXfile:Component + element pathPricingCard.tsx:PricingCard insert-after p.pricing-card__price: …
HTMLfile: CSS-like path, or a map IDindex.html:#pricing .pricing-card[2] .pricing-card__amount text $39
CSSfile:selector[n]styles.css:.pricing-card--highlighted set border 2px solid var(--color-accent)

The operations are few and typed:

  • replace, insert-before, insert-after and delete on a symbol, statement, element or rule.
  • replace-in, a text substitution limited to one symbol.
  • rename, done by the TypeScript language service, so every reference in the project changes too.
  • set and unset for CSS declarations and HTML attributes.
  • text, append and remove for HTML content.

Each read returns a short content hash for what was read. An edit carries the hash it was based on, and the server refuses it when the code has changed since. This stops an edit from landing on code the model never saw.

The round trip

flowchart LR
  A[Project files] -->|parse, watch| B[Index: symbols, landmarks, rules, hashes]
  B --> C[map]
  B --> D[read by address]
  C --> M((AI model))
  D --> M
  M -->|edit ops + hashes| E[Apply to original text spans]
  E --> F[Format changed ranges only]
  F --> G[tsc, ESLint, HTML and CSS parse]
  G -->|pass| H[Write files, update index]
  G -->|fail| R[Roll back, return errors by address]
  R --> M
  H --> M
  1. Index. Parse TypeScript and JavaScript with the TypeScript compiler API, HTML with parse5 and CSS with PostCSS. Update the index when a file changes.
  2. Read. The model calls map, then read for the addresses it needs.
  3. Edit. The model sends edit operations with the hashes it read.
  4. Apply. The server changes only the text spans the operations name. Comments and formatting outside them stay exactly as they were.
  5. Format. The server runs Prettier or Biome on the changed ranges only, so it never reformats a file the user did not ask about.
  6. Check. The server runs tsc and ESLint for code, and parses HTML and CSS again. On failure it rolls back and returns the errors, mapped back to addresses.

Hazards to handle: JSX, decorators and comments attached to nodes; semicolon insertion when code is regenerated; whitespace inside inline HTML elements and <pre>; tags the HTML parser inserts (<tbody>); entities and boolean attributes; CSS rule order, !important, custom properties and @layer. Exclude vendor CSS, minified and generated files from the index.

Measured results

Method. The script builds each view with real parsers (the TypeScript compiler 5.9, parse5 7, PostCSS 8) and counts tokens with OpenAI's o200k_base and cl100k_base tokenizers through js-tiktoken. The corpus is 8 sample files written for this test, 10,364 tokens in all: three TypeScript modules, two React components (one with Tailwind), two HTML pages (one with Tailwind) and one stylesheet.

What these numbers do not show

  • Accuracy. No model ran a task. A smaller view that the model misreads is not a saving. Phase 5 measures pass rates.
  • Claude's tokenizer. No Anthropic API key was available, so OpenAI's tokenizers stand in. The two agree within 1 point, which suggests, but does not prove, that Claude's counts are close.
  • Real repositories. The 8 files were written for this test. They have typical comments, Tailwind and inline icons, but real code may have more or fewer of each. Phase 0 repeats this on 20 public repositories.
  • Scale. The repo map here covers 5 code files. In a 500-file repository the map is larger, so the model reads a map of a folder, not of the whole repository.

Decisions

In

Map, views on request, edits by address, the server-side round trip. These carry most of the saving.

In

Real code as the reading view for TypeScript, JavaScript and CSS. Measured as good as or better than a custom syntax, at no learning cost.

In

Compact views for HTML, and SVG and data-URI elision. They save 12 points over plain HTML, and elision saves 34 more.

In

CSS selector filtering, cross-referenced with the classes in HTML and JSX.

Test

Pug-style JSX (+6 points) and TypeScript without indentation (+8 points). Each stays only if pass rates hold in phase 5.

Out

The repetition view (template plus rows for repeated markup). Left out by your decision.

Out

Inline IDs in reading views. They cost 1-9 points. IDs stay in the map only.

Out

Abbreviated keywords and property names (fn, bg). Tokenizers already treat the full words as single tokens, and models know the full words better.

Out

A new language for the model to write. SimPy needed fine-tuning to keep accuracy, and its saving (about 10-14%) is smaller than what selection and edits give here.

Roadmap

One repository, one npm package with a CLI and an MCP server. The estimates are for one developer working full time, about 27 weeks in all. They are estimates, not measurements.

Phases

  1. Measure before building

    2 weeks

    Repeat this page's measurement on real code before writing the product.

    Work
    • Run the script on 20 public repositories pinned by commit (React apps, Node services, static sites, a Tailwind site).
    • Count with Anthropic's token-counting endpoint as well as tiktoken.
    • Add the cases this sample lacked: decorators, enums, overloads, Vue and Svelte templates (to size later work).
    Deliverable
    A results file in bench/ and a short report.
    Gate
    Map plus code needed is at least 50% smaller than the files an agent opens for the same task, on the median repository. If not, stop or rescope.

  2. Skeleton and core

    2 weeks

    The parts every language shares.

    Work
    • Repository, TypeScript build, Vitest, CI on Windows, macOS and Linux, the Apache-2.0 licence.
    • The address scheme and the edit-operation grammar, written as a spec first.
    • The span patcher: apply edits to original text, refuse overlaps, keep everything else byte for byte.
    • Content hashes and the stale-edit refusal.
    Gate
    Property tests: random edits on random files leave untouched bytes identical, every time.

  3. TypeScript and JavaScript: reading

    3 weeks
    Work
    • Index with the TypeScript compiler API, incremental on file change; respect tsconfig, .gitignore and generated files.
    • The map per file and per folder, with signatures, exports and line ranges.
    • The plain view, and a read by address (function, class, method, type).
    • search: find symbols and references through the language service.
    Gate
    The index of a 5,000-file repository builds in under 30 seconds and updates in under 200 ms after a save (targets, to be measured).

  4. TypeScript and JavaScript: editing

    3 weeks
    Work
    • The operations: replace, insert, delete, replace-in, and rename through the language service.
    • Formatting of changed ranges only, with the project's own Prettier or Biome settings.
    • The check: tsc --noEmit on the affected project, ESLint if configured, roll back on failure, errors mapped to addresses.
    • Undo of the last edit batch.
    Gate
    On 200 scripted edits across the phase-0 repositories, every applied edit type-checks or is rolled back, and no untouched byte changes.

  5. MCP server and CLI

    2 weeks
    Work
    • An MCP server over stdio with six tools: map, read, search, edit, check, undo. Short tool descriptions, since they are sent with every request.
    • The same tools as CLI commands.
    • Set-up guides for Claude Code, Cursor and VS Code.
    • Safety: confine paths to the workspace, never run project scripts, limit file sizes.
    Deliverable
    A first preview release (0.1) for TypeScript and JavaScript only.

  6. Benchmark: tokens and accuracy

    3 weeks

    The phase that decides whether the project continues.

    Work
    • Run the TypeScript tasks of SWE-PolyBench with one agent twice: once with its normal file tools, once with this server. Use the same model and the same prompts.
    • Record input tokens, output tokens, cost (with caching), time and pass rate.
    • A/B the open choices: TypeScript with and without indentation, comments kept or removed.
    Gate
    Total tokens at least 40% lower with a pass rate no more than 1 point lower (tentative thresholds; fix them before the run). If tokens fall but the pass rate falls more, simplify the views and run again.

  7. JSX and TSX

    2 weeks
    Work
    • The Pug-style view for JSX, and element paths inside components as addresses.
    • Operations on JSX elements and attributes.
    • An A/B against plain JSX on the benchmark's React tasks.
    Gate
    The compact view stays only if its pass rate is within 1 point of plain JSX.

  8. HTML

    3 weeks
    Work
    • parse5 index, map of landmarks and headings, compact view.
    • Elision of inline SVG and data: URIs, readable on request.
    • Operations: text, attributes, append, insert, remove, by CSS-like path.
    • Whitespace-safe patching (inline elements, <pre>, entities).
    • A task set of 50 HTML edits, since no public benchmark covers HTML.
    Gate
    Every edit re-parses to the intended tree, and the page's other bytes are unchanged.

  9. CSS

    2 weeks
    Work
    • PostCSS index, map by block (BEM roots, at-rules, custom properties), plain view.
    • Selector filtering: the rules that apply to an element in HTML or JSX, plus the custom properties they use.
    • Operations: set and unset declarations, add and remove rules, in source order.
    Gate
    For each filtered element, a browser's computed style is the same with and without the rules the filter left out (checked with a headless browser on the task pages).

  10. Hardening

    3 weeks
    Work
    • Watch mode, large repositories and monorepos, memory limits.
    • Fuzz the parsers' inputs and the edit grammar; hostile file sizes and paths.
    • Windows paths and line endings (CRLF kept as found).
    • Telemetry off by default; no code leaves the machine.

  11. Release 1.0

    2 weeks
    Work
    • Publish on npm, with the spec of the views and the edit grammar.
    • Publish the benchmark report with its method, so others can reproduce it.
    • Contribution guide, issue templates, a public roadmap.
    After 1.0
    • Vue, Svelte and Astro templates; SCSS and Less; Tailwind-aware class views.
    • Python, the most requested next language for agents.
    • A study of fine-tuning on a compact syntax (the SimPy route), only if the benchmark shows a gap worth it.

The script

The measurement script is count.mjs, about 670 lines of JavaScript. It needs Node 20 or later and four packages: js-tiktoken, typescript, parse5 and postcss.

  1. Run pnpm install --frozen-lockfile --ignore-scripts in the script's folder. It installs the pinned versions. The project uses pnpm only.
  2. Run node count.mjs to measure the sample files and the five tasks.
  3. Run node count.mjs <folder> to measure the views of any project folder. The task tables run only on the samples.
  4. Read the views it writes to out/, and the numbers in out/results.json.
